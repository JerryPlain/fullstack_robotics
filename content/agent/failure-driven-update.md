## 先诊断，再更新

经典 PSO 只看一个标量分数。SwarmAgentic 不一样：先让 LLM **读失败案例**，找出系统具体哪里有毛病，再决定怎么改。

流程：

1. 每个失败的样本，LLM 写一段不超过 150 字的根因分析；
2. 另一个 LLM 把这些分析归纳成**有类型的缺陷**，一共 7 类：

| 智能体层面 | 协作结构层面 |
| --- | --- |
| 缺少角色 | 缺少工作流步骤 |
| 角色冗余 | 工作流步骤冗余 |
| 角色策略不足 | 输入不足 |
| | 输出不合适 |

每一条修改都对准一个**有名字的缺陷**。协作结构上的缺陷尤其危险：一个步骤的输出不对，错误会顺着工作流一路传下去。

## 为什么去掉惯性

PSO 的惯性项是「保持上一步的速度」。可是速度现在是一份文字修改计划，「保持」没有意义。于是换成**失败项**：找出上一轮计划里**没起作用**的那部分。

代码里分两次 LLM 调用：

1. **识别**：对当前每个缺陷，问上一轮计划里有没有针对**完全相同的缺陷**提出过修改？有，就把那条修改记为「失败的修改」；
2. **改进**：针对这些缺陷提出新的操作，并且明确要求「不要重新提出或换个说法重复失败的修改」。

**什么算失败**：一个修改针对的缺陷，下一轮**还在**。分数涨没涨不参与判断。

## 优先级：否决 > 建议

合并三条建议时，失败项的否决优先：不管个人最优和全局最优怎么建议，失败过的修改都不能再来一次。

记忆只有**一轮**深：计划里只保留「缺陷 → 修改」，失败的修改只在下一轮被禁止，不是一张越来越长的黑名单。第一轮没有上一轮计划，直接从缺陷清单生成初始计划。

## 实证上它有多重要

消融（创意写作 20 题，满分 10）：

| 版本 | 分数 |
| --- | --- |
| 完整版 | 8.8 |
| 去掉失败驱动项 | 8.4 |
| 去掉智能体级调整 | 7.3 |
| 去掉协作结构重组 | 6.7 |

论文主打的失败项，去掉只掉 0.4，是三个组件里最少的。而且同一个设置在表里出现了两次，分数差 0.3，噪声和这个效应差不多大。

> [!note] 组件在叙事上的重要性和实证上的重要性经常不一致。写论文、读论文都要看消融，而不是看哪一节写得最长。

## 要小心的地方

- 判断两个缺陷「是不是同一个」，本身是一个模糊的 LLM 判断；
- LLM 的幻觉会顺着优化循环一轮轮传下去（论文的局限里也写了）。
