## 一个粒子是一整个团队

SwarmAgentic 里，被优化的单位不是一个智能体，而是**一整套多智能体系统** $S_i = (\mathcal A_i, W_i)$：

- 每个智能体是三元组 $(I, R, P)$：名字、职责、执行策略；
- 工作流 $W$ 是一个有序的步骤列表，每一步指派给一个智能体；
- 适应度 $J(S)$ 只给整个系统打分，单个智能体没有分数。

打个比方：$I$ 是职位名，$R$ 是岗位描述，$P$ 是操作手册（SOP）。

## 配置长什么样

```json
{
  "roles": [
    {"Name": "Budget Analyst", "Responsibility": "...", "Policy": "1. ... 2. ..."}
  ],
  "workflow": [
    {"Step": 1, "Role": "Budget Analyst", "Input": "...", "Output": "..."}
  ]
}
```

规则：每一步只能指派给一个角色；输入必须来自前面步骤的输出；最后有一个角色负责整合交付。

然后 LLM 把配置**编译成代码**：写一个 `def forward(team)`，用 `team.call(role_name, inputs, output)` 调用各个角色，再用 `exec()` 加载。每次 `team.call` 就是一次 LLM 调用，系统提示是「你是 {name}，你的职责是 {responsibility}……{policy}」。

## 两层「多」

- **PSO 层**：5 个粒子是 5 套互相**竞争**的设计，只共享分数和设计本身；
- **智能体层**：一个粒子里的几个智能体**分工协作**完成任务。

粒子之间是竞争加抄作业，智能体之间才是分工协作。

## 能做哪些修改

| 对象 | 操作 |
| --- | --- |
| 角色 | 新增、修改、删除 |
| 工作流 | 新增步骤、改输入、改输出、删除步骤、调整顺序 |

- 没有「替换」：换角色 = 删除 + 新增；
- **修改一个角色只能改它的策略**，不能改名字和职责（代码里的约束）。小修改是利用，增删是改拓扑、是探索；
- **新增角色门槛很高**：只有当任务需要一个「放进现有角色就会打乱它主要职责」的新职责时才加。这相当于隐式的正则化，防止团队越长越臃肿。

判断顺序：这个缺陷落在某个现有角色的职责范围里吗？在，并且改改策略就能解决 → 改策略；不在 → 新增角色；某个角色多余 → 删掉。

## 一个真实的演化过程（TravelPlanner）

1. 向全局最优学：加了一个**质量保证**角色 → 成功率 11%；
2. 向自己的历史最优学：加了一个**住宿交叉核对**的步骤 → 22%；
3. 失败驱动：把质量保证角色的策略改成要检查预算 → 33%。

对比：ADAS 在 TravelPlanner 上找到的最好系统里**没有住宿相关的智能体**，所以总在房型、最少入住天数这类约束上出错。

## 局限

工作流只是带输入依赖的**顺序步骤**，没有显式的分支、循环或辩论。比 ADAS 那种自由写代码的搜索空间窄，好处是可控、可读。
