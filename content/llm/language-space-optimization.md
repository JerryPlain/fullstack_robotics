## 核心想法

> PSO 说到底只要两个操作：**diff**（比较两个解差在哪）和 **apply**（按差去改）。向量能相减，文本不能；但 LLM 能做「比较」和「修改」这两件事。

「对比全局最优和我，找出我缺的设计」，就是 $g - x$ 在语义上的版本。这是读这篇论文时自己总结出的理解。

## 每一项怎么换成 LLM 调用

| 经典 PSO | SwarmAgentic |
| --- | --- |
| 位置 $x$ | 系统配置（角色 + 工作流的 JSON）+ 生成的 `forward()` 代码 |
| 速度 $v$ | 一张清单：每条是「发现的缺陷 → 建议的修改」 |
| 惯性 $\omega v$ | **失败项** $\mathrm{LLM_{fail}}(v^{(t)}, f^{(t)}, f^{(t+1)})$：上一轮的哪些修改没起作用 |
| $c_1 r_1 (p^* - x)$ | $\mathrm{LLM_{pers}}(x, p^*, f^{(t+1)})$：和自己的历史最优比 |
| $c_2 r_2 (g - x)$ | $\mathrm{LLM_{glob}}(x, g, f^{(t+1)})$：和全局最优比 |
| 三项相加 | $\mathrm{LLM_{vel}}$：把三条建议合并成一份修改计划 |
| $x + v$ | $\mathrm{LLM_{pos}}(x, v)$：按计划改配置 |

三项都以**同一张缺陷清单** $f^{(t+1)}$ 为锚，代码里按缺陷编号把三条建议对齐。

## 分两步：先计划，再修改

$\mathrm{LLM_{vel}}$ 决定**改什么**，$\mathrm{LLM_{pos}}$ 负责**动手改** JSON。分开之后，每一步都能单独检查：计划是人能读懂的「缺陷 → 修改」清单。

比较的 prompt 有两条约束：

- 「从对方身上学，但不要直接照抄」；
- 必须引用对方的**原文**（职责、策略、步骤的输入输出），没有可学的就答 None。

这样比较才是有依据的，而不是泛泛的「对方更好」。

## 结构化输出是串起来的前提

每次调用都用 JSON schema 约束输出（`with_structured_output`），缺陷类型是枚举。只有输出能被代码解析，几个 LLM 调用才能接成一条流水线。

## 论文 vs 代码

- 论文写了系数 $c_f, c_p, c_g$ 和随机因子 $r_f, r_p, r_g$，**代码里都没有**：每一项都只是一个 prompt；
- 优化器温度 0.001，几乎是确定性的。多样性**几乎全部来自初始化时的不同温度**。

## 弱模型也能当优化器

优化器是 GPT-4o-mini，比执行任务的 GPT-4o 还弱。能行的原因：**诊断错误比解决任务容易**。论文没有测更强的优化器会怎样。

## 一条脉络

文本梯度（TextGrad 一类）、EvoPrompt（遗传算法 + LLM 改 prompt）→ Model Swarms（PSO 作用在模型权重上）→ SwarmAgentic（PSO 作用在系统设计这种**符号空间**上）。共同点：把 LLM 当成在文本空间里实现经典优化算子的工具。
